# Scheduled governance that stays focused

[简体中文](../zh-CN/automation.md) · [繁體中文](../zh-TW/automation.md)

After the first governance pass in your chat, add one scheduled task if useful. It uses the same Skill, installed tools and control directory. The AI interprets task evidence; TaskCarry plans and records exact local operations. The Codex walkthrough provides concrete scheduling steps; another host requires its own supported scheduler. Installation alone creates neither a schedule nor another AI service.

## Choose the smallest useful arrangement

| Task | Responsibility | Suggested starting point |
|---|---|---|
| Governance | Receive declared stages, continue unfinished operations, explain current progress and concrete next conditions | Start daily at 06:00 in the project's chosen time zone, matching the main walkthrough; adjust when needed |
| Optional observer | Read current records and runtime information; identify a new failure, inconsistent result or missing evidence | Once daily, after a governance window |
| Separate discovery job | Usually unnecessary at first: governance already inspects registered work | Add only for a distinct source and demonstrated need |

These are examples, not required timings. One governance writer owns a control store and its receiver. An observer is neither a second writer nor an approval step. Keep ordinary task chats working independently. A delayed or missed schedule does not require replaying every missed cycle.

## Copy into the existing governance chat

Reuse the [first governance result](windows-example.md#delivery) already shown in the current chat. If onboarding has not reached that step, complete it once before scheduling. Do not launch another Automation just to demonstrate a report. Use this scheduling request:

> Create a recurring task in this governance chat for the project already connected here, daily at 06:00. Show the resolved time zone and saved schedule. Reuse the completed first governance pass; do not run an extra trial. Keep the current model and permissions. On each run use the governance instructions below; the first daily run also supplies the morning summary. Keep quiet when there is no meaningful change, failure or required user action. Do not create a second control directory or activate schedules for another project.

Attach these durable instructions to the scheduled task:

```text
Continue governance for this chat's explicitly connected project using its installed TaskCarry tools and existing control directory. Use $taskcarry-governance-reconcile and, for a concrete failure, $taskcarry-experience-recovery. Keep project direction and professional acceptance with their existing owners.

Read agenda and only the relevant status detail. Check existing task, checkpoint, delivery, artifact and decision evidence before asking for information. When authorized host tools can read an explicitly connected chat, inspect only changed or specifically missing evidence; otherwise state that coverage is unavailable and continue the work supported by records. Do not infer delivery from file changes or read unrelated chats.

Persist relevant reviewed evidence through observe, reusing unchanged records and checking the previous revision before an update. For a round with selected work, start a run record naming its stages, operations and relevant observations. Keep that selection separate from later arrivals.

Choose a small receiving batch, normally reconcile limit 20, and inspect the actual frozen plan. An agenda page is not an execution scope. Verify already-applied effects before resuming. Within existing authorization execute the exact plan; preserve unfinished operations and checkpoints. Update business/code workspaces only for an actual dependency need, using adopt. Reading shared progress or updating Skills does not require merging business branches.

Use applicable experience after checking its code, scope and current evidence. A refresh_plan suggestion only proposes a new plan. An unchanged conflict needs its concrete condition resolved, not an identical retry loop. Within authorized development scope fix shared defects and validate a candidate separately from the installed runtime. Retain a named next condition when action is unavailable. Do not nest another full governance run or change host permissions, accounts or schedules to repair a task.

Report the selected plan's result separately from all current remaining work. A completed batch is not project completion. Keep paused tasks and agreed retention decisions out of repeated reminders. At a safe boundary leave the exact operation and next step for continuation. Before ending, check actual receipts once and finish the selected run record. Explain any pending objects or changed observations without replaying completed effects; do not restart historical audits to prepare a report. Notify only for a meaningful change, failure or user action. The first daily run adds the concise morning summary.
```

Skills remain in their normal installed locations. The saved task should include these instructions; a link to an earlier transient chat message is insufficient. Use the scheduling tools supplied by the host, then inspect the saved definition. Avoid hand-editing native scheduling files or embedding credentials in prompts.

## Morning summary and optional observation

A useful summary covers: accepted stages and baseline; workspaces that actually adopted code; unresolved technical work and conditions; meaningful artifact or backup decisions; runtime observations and their coverage; next actions and any user decision. Report only meaningful backup candidates; reuse verified backups and existing retention decisions. A summary describes the observed state at its time. Later completion belongs in a later result.

The existing governance AI and host produce these results directly in the chat. The initial result confirms what was actually installed, connected and handled; later runs use the same records to explain changes. There is no separate report service or state page. TaskCarry does not provide a native chat collector or automatic reminder counter; configure reminder policies explicitly for the project.

For an observer, create a separate authorized read-only task with this instruction:

```text
Observe this explicitly connected project's TaskCarry status, agenda and doctor results. Compare the latest completed governance result with its stated scope, current open operations and runtime evidence. Read only; do not receive, adopt, restore, install, edit task states, start another agent or approve the governance writer. Installation status does not prove that every host process has reloaded. Report a new discrepancy or actionable change with its object and evidence; unchanged retained history needs no notice. An unavailable observation is a coverage gap, not proof of failure or success.
```

## Verify the connection you will actually use

Confirm the saved chat/project, cadence, time zone, model settings, tools and runtime access. Reuse the onboarding connection evidence, then inspect the first natural scheduled result. A CLI test does not prove a live MCP connection; a manual governance pass does not prove a scheduled trigger. For Codex, local-file tasks require the computer and desktop app to be available; see the [official scheduled-task documentation](https://learn.chatgpt.com/docs/automations?surface=app). Other hosts need separate capability verification.

TaskCarry limits the selected receiving work and preserves supported interruptions. It does not enforce a wall-clock limit on the AI session, stop arbitrary external commands or coordinate multiple computers. Use the host's stop control and keep the journal intact. [Maintenance and safe continuation](governance-maintenance.md) describes the supported local boundaries.
