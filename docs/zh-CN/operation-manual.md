适用版本：0.2.0rc4。**完整操作、目录和可复制提示词统一以 [Windows 主手册](windows-example.md)为准。** 本页解释工作流与选项，不再提供另一套重复安装流程。

## 推荐的一条接入路线

先手工建立 `TaskCarry`、`TaskCarry/control`、`TaskCarry/toolkit`，解压产品到 `toolkit`；直接在 `control` 新建治理聊天，由该聊天完成安装与接入。`control` 是普通治理目录，保存此项目唯一 `.taskcarry`，不是专业 Git 工作树。

一套 TaskCarry 对应一个现实项目。你先填写**【项目名称】**与**【一句话介绍】**；治理根据真实目录、Git 归属与已有成果判断如何初始化或接续，不要求你选择新项目/已有项目路线。空 TaskCarry 不能被当作没有旧工作的证据。情况不清楚时，治理先简要询问已有成果，或先按主手册第 3.1 节取得原窗口的现场归纳，再决定基线。

需要新专业窗口时填写**【n：新专业窗口数量】**，治理新增 n 个工作区并接续已有编号，再由你新建聊天并选择对应目录。每个窗口的业务输入为**【请填入该对话窗需要实际负责的项目内容】**，不预设业务职责或数量。

| 操作 | 主手册入口 |
|---|---|
| 准备项目介绍与目录 | [项目与目录准备](windows-example.md#choose) |
| 准备目录、解压并在治理聊天安装 | [安装](windows-example.md#install) |
| 明确治理职责与项目绑定 | [治理窗口](windows-example.md#governance) |
| 按需添加专业窗口或接续原窗口 | [专业窗口](windows-example.md#agents) · [原窗口接入](windows-example.md#existing) |
| 接入治理 MCP，保留 CLI 后备 | [MCP 与 CLI](windows-example.md#mcp) |
| 完成首次完整当前状态盘点 | [盘点与接收](windows-example.md#delivery) |
| 按实际登记设置宿主定时任务 | [自动化](windows-example.md#automation) |
| 核对当前是否可以正常工作 | [完成检查](windows-example.md#check) |

采用其他根目录时，在首次初始化前统一选择并生成对应路径；不能直接移动已绑定的项目后继续执行旧计划。

## 谁负责什么

| 对象 | 职责 |
|---|---|
| 用户 | 决定实际项目目标、业务取舍和需要授权的行为。 |
| 治理聊天 | 理解任务与证据关系，调用工具接收成果、核对结果、协调按需采用，解释真正需要动作的问题。 |
| 专业聊天 | 在明确工作区推进实际任务，保留检查点，精确交付稳定阶段。一个任务/工作区保持一个主要写入者。 |
| 接收基线 | 专用干净 Git 工作区，保存已接收成果；不用来写专业 WIP。 |
| TaskCarry 内核 | 保存本地状态，核对计划与实际 Git 条件，执行已支持的接收、采用和恢复动作。 |
| 宿主自动化 | 到指定时间唤醒治理模型；它不是另一个控制库。 |

专业窗口按并行工作需求划分，例如软件、硬件、算法、实验、科研、运营、仿真、文书或管理；不预设部门数量，非并行子任务不必另开窗口。一个任务保持一个主要写入者，其他窗口可以只读复核，或承担明确拆分、不重叠的子任务。

合适的现有工作区可原地复用。多个旧窗口共用同一目录时，推荐选一个保留为主要专业任务窗口；其余需要并行的职责在独立新工作区和新窗口接续。先确认旧写入停止，再按任务范围保存摘要、检查点并转入 WIP，保留原历史，不能只靠提示词改变文件归属。

原窗口接入是同一流程的一部分：用户把主手册的归纳提示词贴到旧窗口 → 旧窗口返回真实现场与任务摘要 → 用户将该回复连同手册的转交提示词交给治理 → 治理核对登记并生成回贴提示词 → 用户贴回原窗口继续工作。原窗口不需要重新立项，也不会因目录为空而被忽略。

## 一次完整盘点与日常接续

首次盘点以 `status.workspaces`、`status.tasks` 和 `PROJECT_MAP.md` 的已登记范围为基础，并核对真实文件与 Git 证据。配置表供人和模型阅读；实际状态与现场不一致时要核对，不能只改表让检查通过。

| 当前情况 | 应保留或执行的内容 |
|---|---|
| 已在可信当前基线中的旧成果 | 记录已知归属，避免重复入队。 |
| 明确稳定且尚未接收的阶段 | 核对冻结提交、原 base、完整路径与任务关系，先计划再接收。 |
| 工作未完或没有提交 | 保存精确检查点、结论与下一步；不宣称已经交付。 |
| 暂停、等待或没有新增变化 | 保留当前节点；没有变化不新增积压或催办。 |
| 工作区需要公共更新 | 确认没有活动写入后，先计划再采用，保全本地工作。 |
| 中断或已出现具体失败 | 先对账实际效果和原操作，再使用适用的已实现恢复动作继续缺步。 |

**状态全覆盖不等于所有未完成成果都要接收。** 治理也不会自动发现应用里所有聊天；未登记的窗口需要通过主手册的接入步骤明确纳入。任务整体完成、阶段接收、业务验收是不同状态。

## MCP、CLI 和定时治理的区别

推荐治理聊天通过 MCP 直接调用工具；CLI 作为可用后备，两者操作同一个 control。安装产生的 MCP 配置片段不等于连接成功，必须完成宿主配置并实际调用确认。

首次有限治理直接在当前聊天展示结果，配置定时任务时复用该结果，不为演示报告额外启动 Automation。定时治理由宿主正式工具创建，使用实际时区和目标；日常结果由同一 AI 依据项目记录形成。运行时读取已登记任务和工作区，不写死专业数量，也不声称扫描全部聊天。

专业任务保持正常推进。接收针对明确阶段；工作区采用只在目标可更新时进行。`paused` 仅是任务状态，不能单独证明其他程序已经停止写入。工具锁串行化自身动作，不代表整个模型回合具有跨程序锁。

## 按需选项与边界

| 需求 | 入口及边界 |
|---|---|
| 私有 Git 保存选定成果和精选记忆 | [完整说明](remote-and-multicomputer.md#private-git)：只有实际提交并推送的文件到达远端；`.taskcarry` 和未提交资料另行一致备份。 |
| 多电脑按任务分支协作 | [完整说明](remote-and-multicomputer.md#multi-computer)：一个集成主机，独立任务分支；当前无跨机共享状态或自动事务迁移。 |
| 明确每个 CLI/MCP 参数 | [命令参考](../COMMANDS.md)。 |
| 理解实际系统边界 | [架构](architecture.md)与[运行范围](../RELEASE_BOUNDARIES.md)。 |

接收计划默认最多选择 20 项、最大 100 项，优先续办未完接收操作；执行前核对冻结范围，其余工作单独报告。条数限制不限制整个 AI 会话的时长。经验记录使用已有恢复实现；操作系统修复和原生账号迁移仍不属于产品职责。

无需为了“全部配置”启用可选功能，也不要求用户运行维护测试。先让自己的项目清楚地保存、交付、接收和接续，按实际需要扩展。
