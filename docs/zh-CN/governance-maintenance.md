# 工作持续推进时，怎样维护治理工具

[English](../en/governance-maintenance.md) · [繁體中文](../zh-TW/governance-maintenance.md)

TaskCarry 把项目记录保存在 control 目录，由安装好的工具处理这些记录。更新工具的目的，是让下一轮继续原来的工作；不需要重建项目、重新提交历史成果，也不需要为了更新一个 Skill 而合并业务分支。

本补充适用于 0.2.0rc5。原安装与操作手册的流程仍然适用。新项目继续使用原手册；已有项目的维护可参考下面的安排。定时任务和可选观察者见[定时治理](automation.md)。

## 三种更新，各自解决一件事

| 更新内容 | 使用方式 |
|---|---|
| 工具与项目 Skills | 在专用运行环境安装选定 wheel，预览 setup 后更新受管理的接入文件，保留原 control 状态。 |
| 共享项目进度 | 从同一个 control 读取 `status` 或 `agenda`；了解进度无需改变专业工作区的 Git 分支。 |
| 专业任务需要的已接收代码或成果 | 使用明确的 `adopt` 计划；这是业务更新，继续核对冲突并保全未完成工作。 |

## 每轮先看当前需要处理的工作

`agenda` 给现有 AI 一份有限清单，包括未完成操作、已提交阶段和需要决定的材料。暂停、等待的任务继续保存，不会因此多出交付义务。已完成历史仍可从完整状态与记录中查询。

```json
{"limit": 20}
```

通过 `taskcarry_agenda` 发送这个请求，也可以把它保存成 JSON 请求文件，使用 CLI 的 `agenda` 动作。返回 `next_cursor` 时可继续翻页；游标绑定同一份当前输入，工作发生变化后应重新选取。比较两次观察时，把先前的 `fingerprint` 作为 `previous_fingerprint`。`changed: false` 不会关闭未完成事项，也不授权再次尝试。

清单不会执行修复、启动另一个 AI 或创建定时任务。匹配到的经验是建议，执行者仍需核对实际效果。已建立索引的状态库只选取当前记录和必要前序，不加载无关的已完成历史。条数上限限制返回内容，不代表全部当前输入处理、数据库查询或 AI 对话有同样的耗时上限。

## 维护当前事项索引

新项目会自动建立派生索引。旧索引或失效索引不会改变原始记录：`agenda` 回退为完整选取，并报告 `storage.upgrade_required`。安装选定工具版本、确认相关治理写入者已安全停止后，对已有 control 运行显式 `upgrade` 动作：

```sh
python -m taskcarry --project ./control upgrade
```

使用实际已有的 control 路径，不重新初始化替代项目。这个动作在同一个事务内只重建派生索引，可安全重复执行，原记录和事件保持不变。之后核对 `storage.mode` 为 `indexed_current_v1`、`storage.upgrade_required` 为 false。这不是包升级器，也不迁移业务文件。旧版客户端再次写入可能使索引重新失效，应先停止使用该旧写入者，再重建。

## 保留核对依据与本轮精确范围

已授权的宿主工具提供相关证据后，`observe` 保存来源引用、已核对版本、登记的任务与工作区，以及明确的阶段或材料关联。相同观察直接复用；变化时需带上前一版本，避免旧信息覆盖较新依据。记录不会抓取聊天、证明来源真实或授予访问权限。保留来源引用，不复制敏感对话正文。

本轮有明确选取的工作时，`run` 以具名阶段、操作和相关观察建立记录。结束时核对这一范围内已记录的终态，列出未完成对象和发生变化的观察，不重放操作，也不把后来新增的工作悄悄加入原范围。先通过相应操作工具核对实际效果；本轮结果汇总这些记录，不是独立的 Git 审计。新增工作与项目总体状态仍需和本轮范围分开说明。

这些变化的设计依据与定向合成检查见[治理演进报告](governance-evolution.md)。

## 安装中断后接着完成

升级前先核对当前接收范围和未完采用。`reconcile` 计划支持 `limit`，默认 20、最大 100，先选未完接收操作，再选新交付，其身份也进入冻结计划。计划完成只覆盖所选范围；后来新增的交付仍待处理并单独报告。agenda 的一页不代表执行范围。

采用准备失败会保留具体错误和检查点，让下一轮从 agenda 找到。解决冲突后，成功后继可明确取代它，原失败继续保留。不要删除记录或在输入未变时重复失败调用。`refresh_plan` 对已证明没有应用效果的操作提供计划建议，不执行替代计划；`verify_and_finalize` 让接收执行者核验已有效果并补齐回执。

Setup 在修改受管理文件前先保存精确安装意图。若中断发生在“文件已经写好，结果尚未登记”之间，再次执行同一安装可以识别已经发生的效果，补齐记录；已经符合目标的文件不必重复重写。

如果你独立编辑了受管理文件，或安装未完就换了另一个候选，工具会保留现场并说明冲突。保留接续记录，使用原候选诊断或续办，不要通过删除元数据来恢复。未受管理的文件，即使恰好与安装包相同，也不会因此被接管。

Setup 更新受管理文件时，请勿同时在其他应用中编辑这些文件。安装锁协调的是安装操作，并不能锁住所有外部编辑器。

## 确认实际使用的是哪个版本

历史来源快照说明当时使用了什么，当前运行观察或采用回执说明现在使用了什么。软件更新时保留两者，不重写历史证据。本版不提供任意旧系统编号导入或全部原生聊天发现能力。

`doctor.runtime` 报告回答本次请求的进程实际导入的包版本、解释器、模块位置，以及项目接入文件的信息。CLI 检查成功不能证明之前打开的 MCP 进程已经重新加载。明确更新配置或重启连接后，还应通过该连接再次核对。

源码指纹描述当前磁盘文件，不能证明长驻进程已替换此前导入的代码。更换运行包后需重启相关 MCP 连接；`loaded_code_verified` 保持 false，不宣称已经验证进程内存中的代码。

TaskCarry 管理自身开发时，治理应从源码工作区之外的固定 wheel 环境运行，下一版本在独立范围开发和验证。相关操作安全结束后再采用新版。Control 目录继续保留：任务、检查点和原回执属于项目，不属于某个工具构建。本版没有提供通用的全自动包升级器或跨状态格式回退引擎。

## 一个治理聊天，分别管理两个仓库范围

一个 control 仍只绑定一条接收基线。包含两个独立仓库的产品，可以使用两份 control，由一个治理聊天维护共同项目总览。Setup 时为两个 MCP 连接明确设置不同的 `server_name`，例如 `product_core` 与 `product_app`；之后的 setup 会保留已选名称。

```json
{"mode": "preview", "server_name": "product_core"}
```

核对预览后，使用相同名称执行 `mode: install`。生成片段仍需要在宿主中明确配置，不会自动生效。两份 control 不要同时写同一个接收工作区；这个安排没有提供跨仓库统一事务或跨电脑锁。

本地治理与用户反馈指向同一问题时，沿用一份产品修正记录。共享实现修正、验证后，再登记各安装环境是否采用。记录了修正方法与实际安装修正，是这项工作的不同步骤。
