適用版本：0.2.0rc4。**完整操作、目錄和可複製提示詞統一以 [Windows 主手冊](windows-example.md)為準。** 本頁解釋工作流程與選項，不再提供另一套重複安裝流程。

## 推薦的一條接入路線

先手工建立 `TaskCarry`、`TaskCarry/control`、`TaskCarry/toolkit`，解壓產品到 `toolkit`；直接在 `control` 建立治理對話，由該對話完成安裝與接入。`control` 是普通治理目錄，儲存此專案唯一 `.taskcarry`，不是專業 Git 工作樹。

一套 TaskCarry 對應一個現實專案。你先填寫**【專案名稱】**與**【一句話介紹】**；治理根據真實目錄、Git 歸屬與已有成果判斷如何初始化或接續，不要求你選擇新專案/已有專案路線。空 TaskCarry 不能被當作沒有舊工作的證據。情況不清楚時，治理先簡要詢問已有成果，或先按主手冊第 3.1 節取得原視窗的現場歸納，再決定基線。

需要新專業視窗時填寫**【n：新專業視窗數量】**，治理新增 n 個工作區並接續已有編號，再由你建立對話並選擇對應目錄。每個視窗的業務輸入為**【請填入該對話窗需要實際負責的專案內容】**，不預設業務職責或數量。

| 操作 | 主手冊入口 |
|---|---|
| 準備專案介紹與目錄 | [專案與目錄準備](windows-example.md#choose) |
| 準備目錄、解壓並在治理對話安裝 | [安裝](windows-example.md#install) |
| 明確治理職責與專案綁定 | [治理視窗](windows-example.md#governance) |
| 按需添加專業視窗或接續原視窗 | [專業視窗](windows-example.md#agents) · [原視窗接入](windows-example.md#existing) |
| 接入治理 MCP，保留 CLI 後備 | [MCP 與 CLI](windows-example.md#mcp) |
| 完成首次完整當前狀態盤點 | [盤點與接收](windows-example.md#delivery) |
| 按實際登記設定宿主定時任務 | [自動化](windows-example.md#automation) |
| 核對當前是否可以正常工作 | [完成檢查](windows-example.md#check) |

採用其他根目錄時，在首次初始化前統一選擇並生成對應路徑；不能直接移動已綁定的專案後繼續執行舊計畫。

## 誰負責什麼

| 對象 | 職責 |
|---|---|
| 使用者 | 決定實際專案目標、業務取捨和需要授權的行為。 |
| 治理對話 | 理解任務與證據關係，呼叫工具接收成果、核對結果、協調按需採用，解釋真正需要動作的問題。 |
| 專業對話 | 在明確工作區推進實際任務，保留檢查點，精確交付穩定階段。一個任務/工作區保持一個主要寫入者。 |
| 接收基線 | 專用乾淨 Git 工作區，儲存已接收成果；不用來寫專業 WIP。 |
| TaskCarry 核心 | 儲存本機狀態，核對計畫與實際 Git 條件，執行已支援的接收、採用和恢復動作。 |
| 宿主自動化 | 到指定時間喚醒治理模型；它不是另一個控制庫。 |

專業視窗按並行工作需求劃分，例如軟體、硬體、演算法、實驗、科研、營運、模擬、文書或管理；不預設部門數量，非並行子任務不必另開視窗。一個任務保持一個主要寫入者，其他視窗可以唯讀複核，或承擔明確拆分、不重疊的子任務。

合適的現有工作區可原地重用。多個舊視窗共用同一目錄時，推薦選一個保留為主要專業任務視窗；其餘需要並行的職責在獨立新工作區和新視窗接續。先確認舊寫入停止，再按任務範圍儲存摘要、檢查點並轉入 WIP，保留原歷史，不能只靠提示詞改變檔案歸屬。

原視窗接入是同一流程的一部分：使用者把主手冊的歸納提示詞貼到舊視窗 → 舊視窗返回真實現場與任務摘要 → 使用者將該回覆連同手冊的轉交提示詞交給治理 → 治理核對登記並生成回貼提示詞 → 使用者貼回原視窗繼續工作。原視窗不需要重新立項，也不會因目錄為空而被忽略。

## 一次完整盤點與日常接續

首次盤點以 `status.workspaces`、`status.tasks` 和 `PROJECT_MAP.md` 的已登記範圍為基礎，並核對真實檔案與 Git 證據。設定表供人和模型閱讀；實際狀態與現場不一致時要核對，不能只改表讓檢查通過。

| 當前情況 | 應保留或執行的內容 |
|---|---|
| 已在可信當前基線中的舊成果 | 記錄已知歸屬，避免重複入隊。 |
| 明確穩定且尚未接收的階段 | 核對凍結提交、原 base、完整路徑與任務關係，先計畫再接收。 |
| 工作未完或沒有提交 | 儲存精確檢查點、結論與下一步；不宣稱已經交付。 |
| 暫停、等待或沒有新增變化 | 保留當前節點；沒有變化不新增積壓或催辦。 |
| 工作區需要公共更新 | 確認沒有活動寫入後，先計畫再採用，保全本機工作。 |
| 中斷或已出現具體失敗 | 先對帳實際效果和原操作，再使用適用的已實現恢復動作繼續缺步。 |

**狀態全覆蓋不等於所有未完成成果都要接收。** 治理也不會自動發現應用裡所有對話；未登記的視窗需要通過主手冊的接入步驟明確納入。任務整體完成、階段接收、業務驗收是不同狀態。

## MCP、CLI 和定時治理的區別

推薦治理對話通過 MCP 直接呼叫工具；CLI 作為可用後備，兩者操作同一個 control。安裝產生的 MCP 設定片段不等於連接成功，必須完成宿主設定並實際呼叫確認。

首次有限治理直接在目前對話展示結果，設定定時任務時重用該結果，不為示範報告額外啟動 Automation。定時治理由宿主正式工具建立，使用實際時區和目標；日常結果由同一 AI 依據專案記錄形成。執行時讀取已登記任務和工作區，不寫死專業數量，也不聲稱掃描全部對話。

專業任務保持正常推進。接收針對明確階段；工作區採用只在目標可更新時進行。`paused` 僅是任務狀態，不能單獨證明其他程式已經停止寫入。工具鎖循序執行自身動作，不代表整個模型回合具有跨程式鎖。

## 按需選項與邊界

| 需求 | 入口及邊界 |
|---|---|
| 私有 Git 儲存選定成果和精選記憶 | [完整說明](remote-and-multicomputer.md#private-git)：只有實際提交並推送的檔案到達遠端；`.taskcarry` 和未提交資料另行一致備份。 |
| 多電腦按任務分支協作 | [完整說明](remote-and-multicomputer.md#multi-computer)：一個整合主機，獨立任務分支；當前無跨機共享狀態或自動事務遷移。 |
| 明確每個 CLI/MCP 參數 | [指令參考](../COMMANDS.md)。 |
| 理解實際系統邊界 | [架構](architecture.md)與[執行範圍](../RELEASE_BOUNDARIES.md)。 |

接收計畫預設最多選取 20 項、最大 100 項，優先接續未完接收操作；執行前核對凍結範圍，其餘工作個別回報。條數限制不限制整個 AI 對話的時長。經驗記錄使用既有恢復實作；作業系統修復和原生帳號遷移仍不屬於產品職責。

無需為了“全部設定”啟用可選功能，也不要求使用者執行維護測試。先讓自己的專案清楚地儲存、交付、接收和接續，按實際需要擴展。
