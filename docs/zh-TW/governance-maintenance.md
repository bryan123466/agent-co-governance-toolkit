# 工作持續推進時，如何維護治理工具

[English](../en/governance-maintenance.md) · [简体中文](../zh-CN/governance-maintenance.md)

AGCT 將專案記錄保存在 control 目錄，由已安裝的工具處理這些記錄。更新工具的目的，是讓下一輪接續原有工作；不需要重建專案、重新提交歷史成果，也不需要為了更新一個 Skill 而合併業務分支。

本補充適用於 0.2.0rc3。原安裝與操作手冊的流程仍然適用。新專案繼續使用原手冊；既有專案的維護可參考下列安排。定時任務與可選觀察者見[定時治理](automation.md)。

## 三種更新，各自解決一件事

| 更新內容 | 使用方式 |
|---|---|
| 工具與專案 Skills | 在專用執行環境安裝選定 wheel，預覽 setup 後更新受管理的接入檔案，保留原 control 狀態。 |
| 共用專案進度 | 從同一 control 讀取 `status` 或 `agenda`；了解進度無需變更專業工作區的 Git 分支。 |
| 專業任務需要的已接收程式碼或成果 | 使用明確的 `adopt` 計畫；這是業務更新，繼續核對衝突並保全未完成工作。 |

## 每輪先看目前需要處理的工作

`agenda` 提供現有 AI 一份有限清單，包括未完成操作、已提交階段與需要決定的材料。暫停、等待的任務持續保留，不會因此增加交付義務。已完成歷史仍可從完整狀態與記錄查詢。

```json
{"limit": 20}
```

透過 `agct_agenda` 傳送此請求，也可將其儲存為 JSON 請求檔案，使用 CLI 的 `agenda` 動作。返回 `next_cursor` 時可繼續翻頁；游標綁定同一份目前輸入，工作變更後應重新選取。比較兩次觀察時，將先前的 `fingerprint` 作為 `previous_fingerprint`。`changed: false` 不會關閉未完成事項，也不授權再次嘗試。

清單不會執行修復、啟動另一個 AI 或建立定時任務。符合條件的經驗是建議，執行者仍須核對實際效果。筆數上限限制返回內容，不代表整個資料庫查詢或 AI 對話具有相同的耗時上限。

## 安裝中斷後接續完成

升級前先核對目前接收範圍與未完採用。`reconcile` 計畫支援 `limit`，預設 20、最大 100，先選未完接收操作，再選新交付，其身分也進入凍結計畫。計畫完成只涵蓋所選範圍；後來新增的交付仍待處理並個別報告。agenda 的一頁不代表執行範圍。

採用準備失敗會保留具體錯誤與檢查點，讓下一輪從 agenda 找到。解決衝突後，成功後繼可明確取代它，原失敗繼續保留。不要刪除記錄或在輸入未變時重複失敗呼叫。`refresh_plan` 對已證明沒有套用效果的操作提供計畫建議，不執行替代計畫；`verify_and_finalize` 讓接收執行者核驗既有效果並補齊回執。

Setup 在修改受管理檔案前先儲存精確安裝意圖。若中斷發生在「檔案已寫好，結果尚未登記」之間，再次執行同一安裝可辨識已發生的效果並補齊記錄；已符合目標的檔案不必重複重寫。

如果你獨立編輯了受管理檔案，或安裝未完成就換成另一個候選，工具會保留現場並說明衝突。保留接續記錄，使用原候選診斷或續辦，不要透過刪除中繼資料來恢復。未受管理的檔案，即使恰好與安裝包相同，也不會因此被接管。

Setup 更新受管理檔案時，請勿同時在其他應用程式中編輯這些檔案。安裝鎖協調的是安裝操作，並不能鎖住所有外部編輯器。

## 確認實際使用哪個版本

歷史來源快照說明當時使用了什麼，目前執行觀察或採用回執說明現在使用了什麼。軟體更新時保留兩者，不重寫歷史證據。本版不提供任意舊系統編號匯入或全部原生對話探索能力。

`doctor.runtime` 回報回答此次請求的進程實際匯入的套件版本、解譯器、模組位置，以及專案接入檔案的資訊。CLI 檢查成功不能證明先前開啟的 MCP 進程已重新載入。明確更新設定或重新啟動連線後，還應透過該連線再次核對。

原始碼指紋描述目前磁碟檔案，不能證明長駐進程已替換先前匯入的程式碼。更換執行套件後需重新啟動相關 MCP 連線；`loaded_code_verified` 保持 false，不宣稱已驗證進程記憶體中的程式碼。

AGCT 管理自身開發時，治理應從原始碼工作區之外的固定 wheel 環境執行，下一版本在獨立範圍開發與驗證。相關操作安全結束後再採用新版。Control 目錄持續保留：任務、檢查點與原回執屬於專案，不屬於某個工具建置。本版沒有提供通用的全自動套件升級器或跨狀態格式回退引擎。

## 一個治理對話，分別管理兩個儲存庫範圍

一個 control 仍只綁定一條接收基線。包含兩個獨立儲存庫的產品，可使用兩份 control，由一個治理對話維護共同專案總覽。Setup 時為兩個 MCP 連線明確設定不同的 `server_name`，例如 `product_core` 與 `product_app`；之後的 setup 會保留已選名稱。

```json
{"mode": "preview", "server_name": "product_core"}
```

核對預覽後，使用相同名稱執行 `mode: install`。產生的片段仍需要在宿主中明確設定，不會自動生效。兩份 control 不要同時寫入相同接收工作區；此安排沒有提供跨儲存庫統一交易或跨電腦鎖。

本地治理與使用者回饋指向相同問題時，沿用一份產品修正記錄。共用實作修正、驗證後，再登記各安裝環境是否採用。記錄修正方法與實際安裝修正，是此項工作的不同步驟。
