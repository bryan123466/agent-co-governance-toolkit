# Governance reconciliation / 治理接收

Start with `taskcarry_agenda` for a bounded current-work selection. Follow `next_cursor` while the input fingerprint remains valid; changed input requires a fresh selection. `changed: false` is a comparison, not proof that pending work is resolved. The agenda never executes, retries or starts another agent. Use `taskcarry_status` when full recorded detail is needed. Distinguish explicit deliveries from checkpoints and unchanged retained task state. Use task, artifact and commit evidence to understand relationships. Formatting differences or an old observation alone do not prove a current business fault. Missing evidence remains missing; do not fabricate author statements or approvals.

When relevant host evidence is available within the user's scope, use `taskcarry_observe` to preserve the reviewed source reference, source revision, task/workspace and explicit relationships. Read existing observations in `status.continuity` when needed; reuse unchanged evidence and use its `expected_revision` for updates. The engine validates record relationships, not the truth of chat content. A changed source or deliverable requires rechecking the affected relationship, not rescanning every conversation. Missing host access remains a concrete next condition, not proof that the material is unrelated.

For a multi-step intake, use `taskcarry_run` to freeze the selected stage, operation and observation identities. Resume an unfinished recorded run before creating a duplicate. `mode: finish` checks durable terminal receipts for that selection and retains unfinished items; it does not execute Git or certify current external files again. Inspect changed observations separately. A completed run never closes the entire project or erases later deliveries. An empty initial onboarding review need not invent a run or task.

Call `taskcarry_reconcile` with the registered baseline, `execute: false` and a suitable `limit` (default 20, maximum 100). The count bounds selected receiving work, including unfinished receipts; an agenda page is not an execution scope. Inspect the actual returned plan, then execute that exact `plan_id` within existing user authorization. Plan completion only covers its frozen selection: inspect the separately reported remaining work before describing the current queue. A later delivery belongs to a later plan. First verify the actual effects of unfinished operations and resume applicable missing steps. When relevant inputs invalidate a plan and no applied effect requires continuation, inspect the error and request a fresh plan. Do not force an update, add unlisted paths, replay an accepted stage, push remotely, or declare business acceptance.

Use `taskcarry_adopt` only when a task needs the accepted business/code baseline, previewing and executing its exact plan. Preserve local commits, index, unstaged and new files. Updating toolkit Skills or reading shared progress does not require adopting a business branch. A specific conflict limits that workspace; unrelated tasks continue. The tools' own scope checks do not constrain arbitrary shell commands or grant new user permissions.

Report actual accepted stages, retained work, actionable failures and the next condition directly in the governance chat. For the first onboarding pass, also state the installed version, connection actually checked and registered workspaces/tasks. An empty project can be ready for work; do not invent tasks, commits or deliveries. Reuse that result for schedule setup instead of launching a demonstration Automation. The same Skill and tools support manual and scheduled turns; scheduling is configured separately in the host. Daily reports use existing records, without a separate reporting service.

For a schedule, keep one governance writer for this control store and receiving baseline. An optional observer only reads. Read current records before requesting chat context; when authorized host tools expose relevant chats, inspect only changed or specifically missing evidence. TaskCarry does not discover or read chats itself. A scheduled turn need not scan every historical receipt or exhaust every page. Finish its selected work or preserve an explicit next condition; use the host's stop mechanism at a safe boundary. TaskCarry has no hard AI-session timer. Separate a deep product repair from a routine intake, and keep independent professional work moving. Notify on meaningful change, failure or required action; unchanged retained work does not need repeated reminders.
