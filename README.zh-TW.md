# Agent Co-Governance Toolkit

**讓長期 Codex 專案在多個獨立工作區之間，維持清楚的狀態、可接續的任務與有依據的協作。**

[English](README.md) · [简体中文](README.zh-CN.md) · [繁體中文](README.zh-TW.md)

[下載 v0.2.0rc1](https://github.com/bryan123466/agent-co-governance-toolkit/releases/tag/v0.2.0rc1) · [Windows 完整手冊](docs/zh-TW/windows-example.md) · [互動式工作流程](docs/index.html#zh-TW)

**版本 0.2.0rc1，候選發行版。** 適合已經使用 Codex 與 Git 的使用者。向治理對話提供專案名稱與簡短介紹，接入實際使用的工作區，專業對話就能沿用一份共同的任務、成果與下一步紀錄，繼續推進原有工作。

本公開工具是通用治理能力的獨立實作，不是任何私有正式環境治理系統的完整原始碼。文件列明的候選版功能，不需要隱藏的私有模組才能執行。

## 為什麼需要它？

長期專案的狀態往往分散在對話、工作檔案、提交與報告中。任務暫停不等於失敗；某個成果可以交付，但整個任務還沒結束；治理下一輪執行前，可能已經產生好幾個版本；Git 操作也可能實際完成，卻尚未寫完回執。

AGCT 為這些情況保留不同的紀錄與處理方式：保存任務目前的位置，接收明確宣告的穩定階段，並在條件允許時，讓已登記的工作區採用共同基線。歷史仍可追溯，但不把每個舊任務都變成需要反覆處理的佇列項目。

你繼續做專案決定、與 Codex 協作。工具提供治理流程共用的執行層，不要求所有人另外手動維護一套專案管理系統。

## 整個專案如何協作？

![專案治理流程：使用者方向、治理 AI 與統一核心、專業工作區、穩定交付及接續工作](docs/assets/governance-flow.zh-TW.svg)

[開啟可離線使用的互動說明](docs/index.html#zh-TW)。圖中呈現職責與工作循環，不代表工具能夠自動存取全部對話或外部系統。

| 參與者 | 主要職責 |
|---|---|
| **使用者** | 決定專案方向、分配職責，並負責業務驗收、重要取捨與額外對外傳送等決定。 |
| **治理對話** | 運用 AI 理解任務證據與關聯，維護目前的專案狀態，準備接收與工作區更新計畫，核對實際結果，說明具體需要使用者決定或操作的事項。 |
| **1～n 個專業對話** | 在已登記的工作區推進各自任務，保留未完成工作與下一步，在穩定節點宣告交付；依序進行的子任務可以留在同一對話。 |
| **統一工具核心** | 記錄狀態，檢查明確輸入與執行條件，執行已支援的本機操作，並保留 CLI 與 MCP 均可讀取的回執。 |

一份 control 對應一個實際專案、一條接收基線，以及該專案所需的多個任務工作區。專業工作不必等待整個專案或無關任務全部完成；更新某個工作區時，仍需與該工作區的寫入者協調。

## 工作區可以如何安排？

<img src="docs/assets/workspace-sidebar-example.png" alt="Codex 側邊欄的通用專案組織示意，包含治理與不同專業職責的對話" width="360">

這是依照介面樣式製作的**通用組織示意圖**，不是工具自動建立的實際安裝截圖。專業角色與數量由你的專案決定；圖中的軟體、硬體、演算法等只是範例。

專案管理與治理可以在同一對話中區分職責，也可以依需要分開。備用對話與觀察對話都不是工具的必要組成。重點是實際任務、工作區與寫入範圍對得上，而不是複製一模一樣的側邊欄。

## AI 判斷與統一執行核心各做什麼？

- **Codex 提供 AI 能力。** 理解指令、閱讀相關證據、判斷任務邊界，並提出或選擇下一項受支援的操作。
- **AGCT 提供持久紀錄與經過檢查的操作。** 任務狀態、檢查點、凍結階段、計畫、回執與經驗規則，保存在對話的暫時上下文之外。
- **CLI 與 MCP 呼叫同一個核心。** MCP 將 `agct_status`、`agct_checkpoint` 等工具直接提供給 Codex；CLI 透過 Python 呼叫相同實作，兩者共用同一份 control 狀態。
- **專案技能說明工作方法。** 公開套件包含專案安裝、任務交付、治理接收與經驗恢復四類技能。技能指引工具使用，不授予原生權限，也不構成作業系統層級的沙盒。

工具本身不訓練模型權重、不呼叫模型 API，也不另外建立 AI 服務。寫好一筆經驗紀錄，同樣不等於自動產生新的可執行恢復能力。

## 日常工作循環如何運作？

**工作 → 視需要保留檢查點 → 宣告穩定階段 → 計畫與接收 → 條件允許時採用 → 接續工作**

| 環節 | 實際意義 |
|---|---|
| **維護任務** | 維持穩定的任務識別、目前狀態、相關決定與下一步。沒有變化的暫停或等待任務，保留接續位置。 |
| **保存檢查點** | 保留選定且已存入磁碟的檔案與接續資訊；檢查點不是交付，也不是全部對話歷史的副本。 |
| **宣告穩定階段** | 明確指定真實 Git base、commit 與完整變更路徑。專業工作區的後續編輯，不會悄悄改變這份凍結交付。 |
| **計畫與接收** | 先核對整合計畫，再執行受支援的操作，確認實際效果後記錄完成；技術接收不取代業務驗收。 |
| **採用共同基線** | 對符合條件的工作區執行更新，保全支援範圍內的本機提交、暫存、未提交變更與新檔案。忙碌或有衝突的對象，說明下一個條件，不強制覆寫。 |
| **接續或恢復** | 沿用有效回執。已知問題有適用且已實作的恢復動作時，核對目前條件與實際效果，只補未完成步驟；未知問題需要診斷，不無限重試。 |

**檢查點 ≠ 交付 ≠ 業務驗收。** 接收一個階段不代表整個任務結束。新版本取代舊階段，必須有明確的累計關係、提交祖先與範圍涵蓋證據，不能只因時間較晚，就捨棄獨立成果。累計 `supersedes` 仍須符合目前同任務、同工作區的契約。

工具也支援登記素材引用，例如不適合納入指定檔案檢查點的大型檔案。引用紀錄或備份決定不等於備份已經存在，仍需實際證據支持。

## 三步開始使用

1. **準備產品。** 下載具名的 [v0.2.0rc1 版本](https://github.com/bryan123466/agent-co-governance-toolkit/releases/tag/v0.2.0rc1)，依照 [Windows 準備步驟](docs/zh-TW/windows-example.md#choose)操作；具體目錄與指令由主手冊提供。
2. **建立治理對話。** 填寫 **【專案名稱】**與 **【一句話介紹】**，使用[安裝提示詞](docs/zh-TW/windows-example.md#install)。治理先核對實際工作，再判斷初始化或接續；空的安裝目錄不代表專案沒有舊成果。
3. **接入工作並盤點目前狀態。** 接入既有對話或增加專業工作區，依條件設定[治理 MCP](docs/zh-TW/windows-example.md#mcp)，完成[首次目前狀態盤點](docs/zh-TW/windows-example.md#delivery)。CLI 透過相同核心，保留為可用的備用入口。

README 負責介紹產品，Windows 主手冊是唯一詳細操作指南，提供可複製的提示詞與清楚的填寫位置。一般使用者開始自己的實際專案，不需要先執行開發維護測試。

## 既有對話與任務歷史如何保留？

接入治理不要求放棄正在使用的對話。

**原視窗整理接入回覆 → 將回覆與轉交提示詞一起傳給治理 → 治理登記並核對實際綁定 → 將產生的接續提示詞貼回原視窗。**

接入回覆包含實際目錄、Git 歷史、成果、未完成工作、決定與下一步。它保留任務與相關歷史，不必把整段對話紀錄全部複製到治理。工具不會自動掃描 App 內所有對話。

多個原視窗共用同一目錄時，在原處保留一個主要專業寫入者。確實需要並行的職責使用獨立工作區；先保全精確範圍的 WIP 與接續資訊，再停止原視窗對該範圍的寫入並交接。不同對話名稱，不能隔離檔案或 Git index。

詳見[接續既有視窗](docs/zh-TW/windows-example.md#existing)。

## 依需要增加 1～n 個專業工作區

提供 **【n：本次新增專業工作區數量】**，再指定 **【各視窗實際負責的專案內容】**。

治理核對現有登記、延續既有編號、記錄本次目標清單，並為每個新工作區產生已填好路徑與編號的提示詞。同一次準備操作中斷後，應沿用清單中已完成的對象，不再重複新增一批。接著由你逐一建立新對話，選擇清單中的目錄，貼入對應提示詞。

不預設部門結構、示範業務或固定三個視窗。依真正需要並行的職責或獨立子任務拆分。新的業務任務使用新的穩定任務識別；轉來的舊任務保留原識別與證據。

詳見[增加專業工作區](docs/zh-TW/windows-example.md#agents)。

## 可以視需要增加哪些能力？

| 選用設定 | 帶來的作用 | 必須明確的邊界 |
|---|---|---|
| **排程治理** | 由宿主在指定時間喚醒治理對話，讀取目前已登記的任務與工作區，接收新階段、報告變化並執行適用更新。 | 排程由宿主建立；AGCT 不是排程器，保存提示詞也不等於已經成功執行。 |
| **私有 Git 記憶庫** | 透過精確範圍的提交與推送，保存已接收成果及精選任務說明。 | 遠端推送是另一項操作；Git 不自動保存未提交檔案、全部對話或使用中的控制資料庫。 |
| **多電腦分工** | 不同電腦在獨立任務分支工作，由一台整合電腦接收成果。 | 尚未完成實際雙電腦端到端驗證；沒有分散式鎖定、自動選主或本機治理資料庫自動合併。 |

先把本機工作流程釐清，再依需要增加排程。遠端或多電腦操作，應建立在實際帳號、存取權限、任務範圍與恢復安排已經明確的基礎上。

## 環境需求與目前邊界

正常專案流程需要 **Python 3.11+**、**Git**，以及用於模型協作的現有 **Codex**。工具執行時使用 Python 標準函式庫，AGCT 本身不額外引入執行期 Python 相依套件或模型 API 訂閱；以 Git 為基礎的檢查點、接收與採用操作需要 Git。

本公開版本每個專案使用一個本機控制資料庫與一條接收基線，以下限制需要理解：

- 工具鎖只讓工具自身的操作依序執行，不能阻止其他編輯器、對話或外部 Git 指令寫入同一目標。每個工作區維持一個主要寫入者，採用更新前做好協調。
- 檢查點保存選定且已存入磁碟的檔案，不包含編輯器未儲存內容、隱含對話狀態或完整儲存庫鏡像；較大素材可用引用方式追蹤。
- MCP 安裝產生的是設定片段，仍需宿主實際設定、必要的專案信任，以及一次成功的工具呼叫，才能確認連線。
- 任務登記不是自動探索所有專案、檔案與對話；任務暫停也不能證明工作區沒有正在寫入的程式或對話。
- 經驗恢復以條件與已實作動作為限，不執行經驗紀錄所附的任意指令，也不修復 Codex、Windows 或其他宿主軟體。
- 遠端發布、原生權限、外部訊息與跨電腦接管，仍是本機核心自動範圍之外的明確操作。

本版本不是私有系統的完整匯出，也不承諾自主修復所有故障。擴大使用範圍前，請閱讀[版本邊界](docs/RELEASE_BOUNDARIES.md)、[運作原則](docs/OPERATING_PRINCIPLES.md)與[安全說明](SECURITY.md)。
