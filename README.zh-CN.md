# Agent Co-Governance Toolkit

**让长期 Codex 项目在多个独立工作区之间保持状态清楚、任务可接续、协作有依据。**

[English](README.md) · [简体中文](README.zh-CN.md) · [繁體中文](README.zh-TW.md)

[下载 v0.2.0rc1](https://github.com/bryan123466/agent-co-governance-toolkit/releases/tag/v0.2.0rc1) · [Windows 完整手册](docs/zh-CN/windows-example.md) · [交互式工作流](docs/index.html#zh-CN)

**版本 0.2.0rc1，发布候选版。** 面向已经使用 Codex 和 Git 的用户。向治理聊天提供项目名称与简短介绍，接入实际使用的工作区，专业聊天就可以沿用一份共同的任务、成果与下一步记录，继续推进原有工作。

本公开工具是对通用治理能力的独立实现，不是任何私有生产治理系统的完整源码。文档列明的候选版功能不需要隐藏的私有模块才能运行。

## 为什么需要它？

长期项目的状态往往分散在聊天、工作文件、提交和报告里。任务暂停不等于失败；某个成果可以交付，但整个任务还没有结束；治理下一轮运行前可能已经产生几个版本；Git 操作也可能实际完成，却没有写完回执。

AGCT 为这些情况保留不同的记录与处理方式：保存任务当前位置，接收明确声明的稳定阶段，并在条件允许时让已登记的工作区采用共同基线。历史仍可追溯，但不把每一个旧任务都变成需要反复处理的队列项。

你继续作项目决定、与 Codex 协作。工具提供治理工作流共用的执行层，不要求所有人另外手工维护一套项目管理系统。

## 整个项目怎样协作？

![项目治理流程：用户方向、治理 AI 与统一内核、专业工作区、稳定交付和接续工作](docs/assets/governance-flow.zh-CN.svg)

[打开可离线使用的交互说明](docs/index.html#zh-CN)。图中表示职责与工作闭环，不代表工具能够自动访问全部聊天或外部系统。

| 参与者 | 主要职责 |
|---|---|
| **用户** | 决定项目方向、分配职责，并负责业务验收、重要取舍和额外外发等决定。 |
| **治理聊天** | 运用 AI 理解任务证据与关联，维护当前项目状态，准备接收与工作区更新计划，核验实际结果，说明具体需要用户决定或操作的事项。 |
| **1～n 个专业聊天** | 在已登记的工作区推进各自任务，保留未完成工作与下一步，在稳定节点声明交付；顺序子任务可以留在同一聊天。 |
| **统一工具内核** | 记录状态，核验明确输入与执行条件，执行已支持的本地操作，并保留 CLI 与 MCP 均可读取的回执。 |

一份 control 对应一个现实项目、一条接收基线，以及该项目实际需要的多个任务工作区。专业工作不必等待整个项目或无关任务全部完成；更新某个具体工作区时，仍需与该工作区的写入者协调。

## AI 判断与统一执行内核各做什么？

- **Codex 提供 AI 能力。** 理解指令、阅读相关证据、判断任务边界，并提出或选择下一项受支持的操作。
- **AGCT 提供持久记录与受检查的操作。** 任务状态、检查点、冻结阶段、计划、回执和经验规则保存在聊天临时上下文之外。
- **CLI 和 MCP 调用同一个内核。** MCP 将 `agct_status`、`agct_checkpoint` 等工具直接提供给 Codex；CLI 通过 Python 调用相同实现，二者共用同一份 control 状态。
- **项目技能说明工作方法。** 公开包包含项目安装、任务交付、治理接收与经验恢复四类技能。技能指导工具使用，不授予原生权限，也不构成操作系统级沙盒。

工具本身不训练模型权重、不调用模型 API，也不另建一个 AI 服务。写好一条经验记录，同样不等于自动产生了新的可执行恢复能力。

## 日常闭环如何运行？

**工作 → 按需保留检查点 → 声明稳定阶段 → 计划与接收 → 条件允许时采用 → 接续工作**

| 环节 | 实际含义 |
|---|---|
| **维护任务** | 保持稳定任务身份、当前状态、相关决定与下一步。没有变化的暂停或等待任务保留接续位置。 |
| **保存检查点** | 保留选定的已落盘文件与接续信息；检查点不是交付，也不是全部聊天历史的副本。 |
| **声明稳定阶段** | 明确真实 Git base、commit 与完整变更路径。专业工作区的后续编辑不会悄悄改变这份冻结交付。 |
| **计划与接收** | 先核对集成计划，再执行受支持的操作，并确认实际效果后记录完成；技术接收不代替业务验收。 |
| **采用共同基线** | 对符合条件的工作区执行更新，保全支持范围内的本地提交、暂存、未提交变化与新文件。忙碌或冲突的对象说明下一条件，不强制覆盖。 |
| **接续或恢复** | 复用有效回执。已知问题有适用且已实现的恢复动作时，核对当前条件与实际效果，只续缺步；未知问题需要诊断，不无限重试。 |

**检查点 ≠ 交付 ≠ 业务验收。** 接收一个阶段不代表整个任务结束。新版本替代旧阶段，必须有明确累计关系、提交祖先与范围覆盖证据，不能仅凭时间更新就丢弃独立成果。累计 `supersedes` 仍须满足当前同任务、同工作区的合同。

工具也支持登记材料引用，例如不适合纳入指定文件检查点的大文件。材料引用或备份决定不等于备份已经存在，仍需实际证据支持。

## 三步开始使用

1. **准备产品。** 下载具名的 [v0.2.0rc1 版本](https://github.com/bryan123466/agent-co-governance-toolkit/releases/tag/v0.2.0rc1)，按 [Windows 准备步骤](docs/zh-CN/windows-example.md#choose)操作；具体目录与命令由主手册提供。
2. **建立治理聊天。** 填写 **【项目名称】**和 **【一句话介绍】**，使用[安装提示词](docs/zh-CN/windows-example.md#install)。治理先核对实际工作，再判断初始化还是接续；空的安装目录不代表项目没有旧成果。
3. **接入工作并盘点当前状态。** 接入已有聊天或增加专业工作区，按条件配置[治理 MCP](docs/zh-CN/windows-example.md#mcp)，完成[首次当前状态盘点](docs/zh-CN/windows-example.md#delivery)。CLI 通过相同内核保留为可用后备入口。

README 负责介绍产品，Windows 主手册是唯一详细操作指南，提供可复制提示词和清楚的填写位置。普通用户开始自己的实际项目，不需要先运行开发维护测试。

## 既有聊天与任务历史怎样保留？

接入治理不要求放弃正在使用的对话。

**原窗口整理接入回复 → 将回复与转交提示词一起发送给治理 → 治理登记并核对真实绑定 → 将生成的接续提示词贴回原窗口。**

接入回复包含真实目录、Git 历史、成果、未完成工作、决定与下一步。它保留任务与相关历史，不需要把整段聊天记录全部复制到治理。工具不会自动扫描 App 内所有聊天。

多个原窗口共用同一目录时，在原处保留一个主要专业写入者。确实需要并行的职责使用独立工作区，在保全精确范围的 WIP 与接续信息后，停止原窗口对该范围的写入再交接。不同聊天名字不能隔离文件或 Git index。

详见[接续已有窗口](docs/zh-CN/windows-example.md#existing)。

## 按需要增加 1～n 个专业工作区

提供 **【n：本次新增专业工作区数量】**，再指定 **【各窗口实际负责的项目内容】**。

治理核对现有登记、接续已有编号、记录本次目标清单，并为每个新工作区生成已经填好路径与编号的提示词。同一次准备操作中断后，应复用该清单中已完成的对象，不再重复新增一批。随后由你逐个新建聊天，选择清单中的目录并贴入对应提示词。

不预设部门结构、演示业务或固定三个窗口。按真正需要并行的职责或独立子任务拆分。新的业务任务使用新的稳定任务身份，转来的旧任务保留原身份与证据。

详见[增加专业工作区](docs/zh-CN/windows-example.md#agents)。

## 可以按需增加哪些能力？

| 可选配置 | 带来的作用 | 必须明确的边界 |
|---|---|---|
| **定时治理** | 由宿主到点唤醒治理聊天，读取当前已登记任务与工作区，接收新阶段、报告变化并执行适用更新。 | 调度由宿主创建；AGCT 不是调度器，保存了提示词也不等于已经成功运行。 |
| **私有 Git 记忆库** | 通过精确范围的提交与推送，保存已接收成果及精选任务说明。 | 远端推送是另一个操作；Git 不自动保存未提交文件、全部聊天或活跃控制库。 |
| **多电脑分工** | 不同电脑在独立任务分支工作，由一台集成电脑接收成果。 | 尚未完成真实双电脑端到端验证；没有分布式锁、自动选主或本地治理库自动合并。 |

先把本地工作流用清楚，再按需增加调度。远端或多电脑操作，应建立在真实账号、访问权限、任务范围与恢复安排已经明确的基础上。

## 环境要求与当前边界

正常项目流程需要 **Python 3.11+**、**Git**，以及用于模型协作的现有 **Codex**。工具运行时使用 Python 标准库，不由 AGCT 额外引入运行时 Python 依赖或模型 API 订阅；基于 Git 的检查点、接收与采用操作需要 Git。

本公开版本每个项目使用一个本地控制库和一条接收基线，以下限制需要理解：

- 工具锁只串行化工具自身的操作，不能阻止其他编辑器、聊天或外部 Git 命令写入同一目标。每个工作区保持一个主要写入者，采用更新前做好协调。
- 检查点保存选定的已落盘文件，不包含编辑器未保存内容、隐含对话状态或完整仓库镜像；较大材料可用引用方式跟踪。
- MCP 安装生成的是配置片段，仍需宿主实际配置、必要的项目信任和一次成功工具调用，才能确认连接。
- 任务登记不是自动发现所有项目、文件与聊天；任务暂停也不能证明工作区没有活动写入者。
- 经验恢复以条件和已实现动作为限，不执行经验记录携带的任意指令，也不修复 Codex、Windows 或其他宿主软件。
- 远端发布、原生权限、外部消息和跨电脑接管，仍是本地内核自动范围之外的明确操作。

本版本不是私有系统的全量导出，也不承诺自主修复所有故障。扩大使用范围前，请阅读[版本边界](docs/RELEASE_BOUNDARIES.md)、[运行原则](docs/OPERATING_PRINCIPLES.md)与[安全说明](SECURITY.md)。
